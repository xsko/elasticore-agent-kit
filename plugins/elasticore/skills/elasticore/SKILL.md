# ElastiCORE

ElastiCORE reads a YAML DSL in `src/main/resources/blueprint/<domain>/` and generates a Spring Boot
application from it: JPA entities, DTOs, repositories, services, REST controllers, access checks,
state transitions and, on request, a TypeScript client.

**The DSL is the source of truth.** Change what the application *is* - its data, who may do what,
how a record moves along, how a value is decided - in YAML, regenerate, and write by hand only the
logic the DSL cannot express, in the files the generator hands over to you.

## 1. Read the project's own guides first

Every generation copies the guides of the ElastiCORE version the project uses into
`src/main/resources/blueprint/`. They are the reference; syntax differs between versions, so read
them rather than relying on memory. They are written in Korean - answer the user in their language.

| Guide | For |
|---|---|
| `elasticore-dsl-guide.md` | Entities, fields and types, relations, DTOs, enums, search conditions |
| `elasticore-annotation-guide.md` | Every `@annotation` and what it generates |
| `elasticore-env-guide.md` | `env.yml`: packages, naming, generation settings |
| `elasticore-dsl-port-guide.md` | Ports: HTTP calls to other systems, SQL through DBMS ports |
| `elasticore-dev-guide.md` | Which files you may edit, preserved blocks, the build |
| `elasticore-rule-guide.md` | The 3.0 rule engine: architectures, bundles, `publisher.rules` |
| `elasticore-ddd-customize-guide.md`, `elasticore-rule-dev-guide.md` | A project's own rule sets |
| `elasticore-migration-guide.md` | Moving a 2.x project to 3.0 |

No guides in the folder means generation has never run: run it once (section 4).
Find a topic with a search over `src/main/resources/blueprint/*.md` before reading a whole guide.

## 2. Who owns a file - read its first lines before you edit it

| Top of the file | Owner | What to do |
|---|---|---|
| `//ecd:...` and nothing else of ElastiCORE's | The generator | Do not edit. It is rewritten from the DSL; after a hand edit the generator skips the file and reports `SKIP(user-modified; -Pforce to overwrite)`, and from then on the file no longer follows the DSL. Change the DSL instead. |
| `//ecd:...` and a block `// !----------` ... `// ------------!` | The generator, except the block | Code inside the block survives regeneration; put yours there. One block per file. |
| `// Initially generated by ElastiCORE; no longer managed - do not remove this line.` | You | Write here - this is where business logic goes. Its Javadoc says what belongs in it. Never delete that line. |
| No ElastiCORE header | You | Ordinary hand-written code. |

Which files a project gets depends on its architecture (`layered`, `ddd`, `hexagonal`), so look at
the headers rather than guessing from names. In `ddd` and `hexagonal` projects a root entity
(`@root`) without `@editable` is split: a generated base (`PurchaseOrderBase`) holds the fields,
and the class of yours (`PurchaseOrder`) is where its operations go. `@behavior` splits an entity
that is not a root the same way.

## 3. Where a change belongs

| The request | Change |
|---|---|
| Store something new; change a type, length or constraint | `fields:` in `model/*.yml` |
| Who may read, create, change or delete | `@access(...)` and `@owner(...)` on the entity's `meta` line |
| How a record moves along (place, ship, cancel) | `states:` |
| A value derived from others; a value kept as it was | `@compute(...)`; `@snapshot(...)` |
| Which API exists | `@expose(...)` on the entity |
| A call to another system, or hand-written SQL | a port - `elasticore-dsl-port-guide.md` |
| Anything the DSL cannot say | a file you own (section 2) |

A worked example that generates and compiles: `references/example-order.md`.

## 4. The loop

1. Read the guide section for what you are about to change.
2. Edit the DSL in `src/main/resources/blueprint/<domain>/` (`env.yml`, `model/*.yml`).
3. Regenerate and compile: `./gradlew compileJava` (`gradlew.bat` on Windows without a Unix shell).
   The plugin runs generation before every compile. To regenerate alone: `./gradlew elcore3` when
   `build.gradle` has an `elasticore { }` block that sets `architecture`, `language` or `rules`,
   otherwise `./gradlew elcore`. The TypeScript client: `./gradlew elcore3ts`.
4. Read the output (section 5) and fix every DSL validation warning before anything else.
5. **Compile even when generation succeeded.** Generation can finish without a warning and the code
   still not compile - a DTO named in `@dtype(...)` that no `dto:` section defines is one such case.
   Generation also succeeds with warnings, so a green Gradle run is not a clean model.
6. Write the remaining logic in files you own. `./gradlew build` runs the tests.
7. Report the change in business terms (section 7).

## 5. Reading the generator's output

Each file gets a line, then a summary: `=== elcore3: 20 written / 0 unchanged / 2 skipped / 0 failed ===`.

| Status | Meaning |
|---|---|
| `WROTE`, `UNCHANGED` | Generated from the DSL as it is now |
| `REGENERATED(owned, never edited)` | A file of yours you had not edited yet, brought up to date |
| `SKIP(user-owned)` | Yours; left alone |
| `SKIP(user-modified; -Pforce to overwrite)` | A generated file was edited by hand - move that change into the DSL or into a file you own, then restore the file (delete it and regenerate) |
| `SKIP(no ElastiCORE header - yours)` | A file at that path that ElastiCORE did not write |
| `SKIP(dontMake)` | Not needed for this model |
| `ERROR ...` | Generation of that file failed - read the message |

Problems in the model are listed under a header - `[elcore3] DSL validation warnings:` from
`elcore3`, `[WARN] DSL Validation Warnings:` from `elcore` - one line each, for example
`[shop] Product.weight: unresolved type 'kilogramz' - no matching Entity, DTO, or Enum found in any domain`.
The build still succeeds with them; the model is wrong until they are gone. `elcore` also reports
hand-edited generated files under `[WARN] User-Modified Files:`.

## 6. Ask the user before you

- run anything with `-Pforce` - it overwrites hand edits in generated files;
- delete a file you own - it is generated again from scratch and the code in it is lost;
- change `@access`, `@owner`, `@login` or `@password` - say who gains or loses access;
- remove or rename a field - a column and an API field disappear, and stored data may go with them;
- change `architecture` or `language` in `build.gradle`.

## 7. Reporting a change

Report what changed for the business before what changed in the code. A reviewer should be able to
approve it without reading Java. Use `references/change-report.md`.

## 8. IDs

On a string key, `@genid` alone generates `IdUtils.newId(<field length>)`: a 3-letter prefix and
(length - 3) random letters and digits. A generator named in `env.yml` (`@env:genid`) or in the
annotation (`@genid(...IdUtils.newId)`) gets `newId()`: 9 random letters whatever the field length.
For tables that will hold many millions of rows use `@genid` alone on `string(15)` or longer, or a
`long @id @sequence` key.
