# Screens on the generated TypeScript client

ElastiCORE writes a TypeScript client from the same model as the server: a function for every
endpoint the server serves, the DTOs as types, the DSL's checks, labels and lifecycle tests. Build a
screen on it - never on `fetch` calls, form rules or labels of your own, which drift from the server
the next time the model changes. The client is plain functions and types, so this page holds for
React, Vue, Svelte or plain DOM alike; ElastiCORE's pet store page (`elasticore-sample-petstore/web`)
uses plain DOM.

## Where it is, and how it stays current

- `./gradlew elcore3ts` writes it into `src/main/ts/`. With `typescriptClient = true` in the
  `elasticore { }` block every build runs it right after `elcore3`; without it a build leaves the
  client as it was, and the build warns `... holds a generated TypeScript client made from an older
  model - run the elcore3ts task after a model change, or set typescriptClient = true ...`.
- One file per type, imported by name: `<Entity>Api.ts` for each entity the API exposes,
  `<Entity>DTO.ts`, `<Entity>SrchDTO.ts` and `<Entity>KeyDTO.ts`, a file per enum and per value
  (`@embeddable`: `Address.ts`), `<Entity>Invariants.ts` where the model declares checks, and
  `apiSupport.ts`, the runtime they share. Each says `Generated by ElastiCORE` in its comment: do
  not edit them for a screen - what the client lacks is a change of the model.
- Write the screens in a folder of their own that reads `src/main/ts`, with their own type check.
  The pet store's `web/`:

  ```json
  { "scripts": { "check": "tsc --noEmit" } }
  ```

  in `web/package.json` (with `typescript` in `devDependencies`), and in `web/tsconfig.json`
  `"strict": true` and `"include": ["src", "../src/main/ts"]`; the screens import
  `'../../src/main/ts/PurchaseOrderApi'`.

## Calls: only through `<Entity>Api`

```ts
import * as Orders from '../../src/main/ts/PurchaseOrderApi';

const page = await Orders.search({ sortCode: 'orderId-', pageSize: 20 });
const order = await Orders.findById(id);           // null when there is none (404)
const placed = await Orders.create(input);          // the row as the server saved it
const shipped = await Orders.ship(id);              // a lifecycle command
```

- What a file has follows the server: `create`, `findById`, `search`, `update`, `batchUpdate`,
  `deleteMany`, `deleteById`; one function per command of a lifecycle (`ship(orderId)`, with the
  command's DTO when it takes one); `export<Entity>(body)` (a `Blob`) where `@expose(methods)` lists
  `export`; `signIn(login, password)`, `signOut()` and `me()` (null for a visitor) on the `@signin`
  entity. An endpoint the server does not serve has no function - `@readonly`, `@expose(methods)`,
  an order that changes by its commands only has no `update` - so a missing function means a missing
  endpoint: change the model, do not call it by hand.
- Every function takes a last, optional `init?: RequestInit` for that one call. For every call:
  `configureApi({ baseUrl, fetch, init })` (or `setApiBaseUrl(url)`) once at start-up - an API on
  another origin, `credentials: 'include'`, a header every request carries.
- An endpoint the client does not have - one controller of your own - goes through `request` from
  `apiSupport`, never a bare `fetch`: it sends JSON with the same base URL and settings and throws
  `ApiError` the same way. The pet store's sign-up:

  ```ts
  import { request } from '../../src/main/ts/apiSupport';
  export const signUp = (customer: CustomerDTO) =>
      request<CustomerDTO>('POST', '/api/petstore/account/signup', customer);
  ```

## Forms: the DSL's checks, labels and codes

- `<Entity>DTO` is the request and the answer. A value never answered (`@password`, `@writeonly`)
  is optional in it.
- `validate<Entity>(value, partial = false)` runs the DSL's checks before sending and answers
  field -> message, empty when nothing is wrong - the same checks the server makes, in the DSL's
  words (`login id is at most 20 characters`, the message of a `@pattern` or a `@min`). Pass
  `partial = true` for an update that sends only what changed: what is required is not asked for.
  A value object has its own: `validateAddress(order.shipTo)`. The server checks again.
- `validate<Entity>Codes(value, partial)` answers the same as `[{ field, code, values }]` - the
  codes of the server's `fieldErrors` (`NotNull`, `Size`, `Min`, `Max`, `Pattern`, `Email`) - for a
  screen that words its messages itself, in another language.
- `<Entity>Fields` holds each field's `label` (the DSL's `-- label`), `labels` per language where
  the DSL gives them, and its limits: `required`, `maxLength`, `minLength`, `min`, `max`, `html` (a
  field the server cleaned, safe to render), or `readOnly` for a value the server sets (`@readonly`,
  `@compute`, `@snapshot`) - show it, do not put it in the form. `<Entity>Meta` is the type's
  own label, `{ label, labels }`, where the DSL gives one.
- `<Entity>Invariants.ts`: `violations(value)` lists the model's promises the value breaks (`price
  must be positive`, `an order needs a line`), `isValid(value)` whether it keeps them all.
- An enum is a constant object of the values the server sends - the code where the enum says
  `@json(code)`: `OrderStatus.PLACED === 'PLC'` - and a type of them. `OrderStatusLabel[value]` is what
  a screen shows (the enum's label column, or the constant's name in words), `OrderStatusLabels`
  the same per language where the enum has `label_en` ... columns, `orderStatusOf(text)` the value
  for a text or `undefined`. A select lists `Object.values(CardType)` with `CardTypeLabel`.

## Buttons: `can<Command>` and `canDelete`

`canShip(order)`, `canCancel(order)` and `canDelete(order)` make the server's own test of the
lifecycle (`states:`, ddd and hexagonal): whether the order's state allows the step now. Show the
button only then. They know nothing of who is signed in, and the state may change meanwhile: the
server still refuses - 403 for a caller the `@access` does not let in, 409 `state.<Entity>.<field>.<command>`
for a state that no longer allows it - so the screen shows the answer.

## Errors: `ApiError`

Every function throws `ApiError` for an answer other than 2xx: `status`, `code` (what was refused,
for a program to branch on), `detail` (what to tell the user, in the request's language),
`fieldErrors` (field -> message of a 400) and `problem`, the whole problem body.

```ts
try {
    await Orders.create(order);
} catch (e) {
    if (e instanceof ApiError && e.status === 400) showErrors(form, e.fieldErrors);
    message.textContent = e instanceof ApiError ? e.detail : String(e);
}
```

| Status | `code` | For the screen |
|---|---|---|
| 400 | `invalid` | `fieldErrors` beside the fields - what `validate<Entity>` did not catch |
| 400 | `no-such-property` | a list sorted by something its answer does not show (below) |
| 401 | `not-signed-in` | send the user to sign in |
| 403 | `forbidden` | the user may not do this: say so, and do not offer it again |
| 404 | `not-found` | the row is gone, or is another's (`@owner`); a reference a request names does not exist (`code` `reference.<Entity>.<field>`). `findById` answers `null` instead |
| 409 | `state.<Entity>.<field>.<command>` | the state does not allow the step: read the row again |
| 409 | `unique`, `stale`, `referenced` | a value another row has; changed by someone else since it was read (read it again); still referenced by another row |
| 422 | `invariant.<Entity>.<rule>` and other rules | the domain refused it: show `detail` |

`me()` answers `null` instead of a 401, `findById` `null` instead of a 404.

## Lists: the search DTO and `Page`

- `search(condition)` takes `<Entity>SrchDTO`: every field optional, a range as `orderedAtFrom` /
  `orderedAtTo`, and the order and the page - `sortCode` (`'orderedAt-,total+'`) or `sortColumn` with
  `sortAscending`, `pageNumber` (from 0) and `pageSize` (the `@expose(20)` size when left out). It
  answers a `Page<T>` - `content`, `totalElements`, `totalPages`, `number`, `size`, `first`, `last` -
  or a plain array where the search is not paged.
- Sort only by what the answer shows - a field of the response DTO, a part of a value it carries
  (`shipTo.city`), the key. Any other - a `@writeonly` or `@password` field, a joined row the answer
  does not carry, a name the entity does not have - is refused with 400 `no-such-property` before
  the query runs (since ElastiCORE 3.0.261124).

## Answers after a write

`create`, `update` and a command answer the row as the server saved it - the state, the values the
server sets (`orderedAt`, totals): show that, not the form's values. With `nestedRows: readers` in
`env.yml` (ElastiCORE 3.0.261127 and later), a nested row of an entity not everyone may read is in what a read answers (`findById`,
`search`), and is `null` in what a create, an update, a command, `me()` and sign-in answer; its
identifier stays. To show it after a write, read the row again with `findById`.

## The loop

After a model change, before saying it is done:

1. Regenerate the client: `./gradlew elcore3ts`, or the build when `typescriptClient = true`.
2. Type-check the screens: `npm run check` in their folder (or `npx tsc --noEmit`). A renamed or
   removed field, a changed type, an endpoint gone - each is a type error here, which would
   otherwise show only when a user opens the screen. Fix the screens, then check again.

The agent kit's hooks remind once of each step that is missing.
