# Example: orders with access rules, a lifecycle and derived values

Three files added to the `shop` domain of `new-project.md`, whose `model/entity.yml` already defines
`Product` (`productId`, `name`, `price: money(10.2)`). They need the 3.0 rule engine with
`architecture = 'hexagonal'` or `'ddd'`; on the 2.x generator the access rules, the lifecycle and the
derived values are not generated at all. Generated and compiled with ElastiCORE 3.0.261015-alpha1,
Spring Boot 4.0.8: no DSL validation warning, `compileJava` passes. The agent kit's CI generates and
compiles them again with the newest ElastiCORE on every change and every week.

## `model/order.yml`

```yaml
entity:
  Customer:
    meta: entity @root @editable @expose(20) @owner(customerId) @access(read=owner, create=public, update=owner) -- customer
    fields:
      customerId: long @id @sequence
      login:      string(20)! @search(eq) @login
      password:   string(255)! @password
      name:       string(50)! @search(like)

  PurchaseOrder:
    meta: entity @root @expose(20) @owner(customerId) @access(read=owner, create=user, cancel=owner) -- order
    fields:
      orderId:    string(36) @id @genid
      customerId: long
      status:     OrderStatus
      total:      money(12.2) @default(0) @compute(sum(lines.subTotal))
      lines:      List<OrderLine> @OneToMany(mappedBy="order") @dtype(List<OrderLineDTO>) @minsize(1, 'the cart is empty')
    states:
      status:
        initial: PLACED
        ship:    PLACED -> SHIPPED
        cancel:  PLACED -> CANCELLED
        delete:  CANCELLED

  OrderLine:
    meta: entity -- order line
    fields:
      lineId:   string(36) @id @genid
      order:    PurchaseOrder @ManyToOne
      product:  Product @ManyToOne
      quantity: quantity! @min(1)
      unitCost: money(10.2) @snapshot(product.price)
      subTotal: money(12.2) @compute(unitCost * quantity)
```

## `model/enum.yml`

```yaml
enumeration:
  OrderStatus:
    meta: enum @db(code) @json(code) -- order status
    fields:
      code:  string(3) @code
      label: string(20)
    enum:
      PLACED:    PLC, Placed
      SHIPPED:   SHP, Shipped
      CANCELLED: CAN, Cancelled
```

## `model/dto.yml`

```yaml
dto:
  OrderLineDTO:
    meta: dto @template(OrderLine)
    fields:
      productName: string @ref(product.name)
```

Without this file `compileJava` fails: `PurchaseOrderDTO` refers to `OrderLineDTO` through
`@dtype(...)`, and only roots get a DTO of their own. Generation itself succeeds - it only lists
`PurchaseOrderDTO.lines: unresolved type 'OrderLineDTO'` under `DSL validation warnings:` - so read
the warnings and always compile after generating.

## Why `customerId: long` and not `customer: Customer @ManyToOne`

With the relation, generation warns
`PurchaseOrder.customer is left out: CustomerDTO is read under @access(read=owner), and a DTO carrying it would show it to whoever reads PurchaseOrder. Its identity stays.`
A customer's record is readable only by that customer, so the order's DTO may not carry it; the
generator drops it and says so. The order needs only to know whose it is - `customerId`, which
`@owner` fills from the sign-in when the order is created, whatever the request sent.

## What the lines say, in business terms

| DSL | Meaning |
|---|---|
| `@owner(customerId)`, `@access(read=owner, create=user, cancel=owner)` | Signed-in users place orders, and an order belongs to whoever placed it - for a customer, `customerId` comes from the sign-in, not from the request; an administrator's request keeps the value it sends. Only that customer, or an administrator, reads or cancels an order: a caller who is not signed in gets 401, another customer gets 404. Operations the list leaves out - `ship`, `delete` - are for an administrator |
| `@access(read=owner, create=public, update=owner)` on `Customer` | Anyone may sign up; a customer reads and changes only their own record (an administrator may too) |
| `@login`, `@password` | The sign-in name; the password is stored as a hash and never returned |
| `states: status:` | An order starts `PLACED`; `ship` and `cancel` are allowed only from `PLACED`; only a `CANCELLED` order may be deleted |
| `@compute(sum(lines.subTotal))`, `@compute(unitCost * quantity)` | The server calculates totals; a client cannot set them |
| `@snapshot(product.price)` | The line keeps the price at the time of the order, even if the product's price changes later |
| `@genid` on `string(36)` | The key is generated: a 3-letter prefix and 33 random letters and digits |
| `@minsize(1, 'the cart is empty')` | An order needs at least one line |

## Files the generator hands over

`PurchaseOrder` is a root without `@editable`, so it is split: `PurchaseOrderBase.java` is
generated, and `PurchaseOrder.java` (with the `Initially generated by ElastiCORE` line) is yours -
the place for operations beyond what `states:` already checks. Each root's `<Entity>Service.java` and
`<Entity>Controller.java`, and `ShopApiErrors.java`, are yours as well. The rest is regenerated
from the YAML - check the headers rather than this list.
