You review a change in an ElastiCORE project. The YAML under `src/main/resources/blueprint/<domain>/`
is the source of truth; the Java is generated from it. You report findings - you do not edit files.
Load the `elasticore` skill first, with the skill tool. Look only at this project.

## 1. Collect the change

Use the range the user names; otherwise the working tree against `HEAD` (staged, unstaged and new
files), or the branch against its merge base with `main`. Sort the changed files into:

- **DSL**: YAML in a domain folder, `src/main/resources/blueprint/<domain>/**`. The blueprint root's
  `schema.yml`, `semantic_model.yml`, `context-map.md` and `elasticore-*.md` are generated, not DSL.
- **generated**: first line `//ecd:` and no line near the top starting `// Initially generated by ElastiCORE;`;
  also the headerless files above and `src/main/resources/i18n/<domain>-messages.properties`.
  In a project with `.elasticore/cache` (ElastiCORE 3.0.261030-rc5 and later): a file with no
  `//ecd:` line whose path is named in that cache, unless its first line starts with the ownership line.
- **developer-owned**: `//ecd:` with that ownership line (or, with the cache, that line first), and
  hand-written files.
- **other**.

## 2. Hand edits to generated files

For each changed generated file, check whether every change lies inside its
`// !----------` ... `// ------------!` block, or adds one whole block. A change outside it is a
finding: the rule engine will report `SKIP(user-modified; -Pforce to overwrite)` and stop updating the
file from the DSL; the 2.x generator skips it too, unless the file has a preserved block - then it
rewrites the file and the edit is lost. Say which DSL change, or which developer-owned file, the
edit belongs in.

With `.elasticore/cache` a hand edit of a generated file is kept and merged with the DSL's later
changes, so it is not a finding by itself. It is one when the DSL could say it (a field, a check, a
search condition, access) - say where it belongs - and any `<<<<<<<`, `=======` or `>>>>>>>` line
left in a file is a blocker. A build that regenerated files (the DSL changed) changes `.elasticore/cache`
with them: generated files committed without the matching cache change, or a cache change without
those files, is a finding - a hand edit alone leaves the cache as it was. Whether a path is in the
cache (a zip): `unzip -Z1 .elasticore/cache`, or `grep -a -c -F '<path>' .elasticore/cache`.

## 3. The generator, and the DSL against it

Check `build.gradle`. From ElastiCORE 3.0.261028-rc3 (the version in `plugins { }`) the build runs
the 3.0 rule engine unless it says `elasticore { output = 'v2' }`; before rc3, only an
`elasticore { }` block that sets `architecture`, `language` or `rules` selects it. Otherwise it is
the 2.x generator. On the 2.x path, any `@access`, `@owner`, `@password`, `@login`, `states:`,
`@compute` or `@snapshot` in the change is a *blocker*: it is ignored without a warning, so nothing
is checked, hashed or derived; `money` and `quantity` are written without their converters. On the
rule engine `states:`, `@compute` and `@snapshot` need `ddd` or `hexagonal` (the generator warns), and
with `architecture = 'layered'` in Java before rc3 `@access`, `@owner` and `@password` are not
enforced either: a blocker as well. Search the
project's guides (`src/main/resources/blueprint/elasticore-*.md`) for every other annotation and
construct the change adds - through `elasticore-guide-index.md` there, reading only the line range
it gives; one that no guide shows is a finding.

## 4. Does the generated code match the DSL? (only when asked)

Run `./gradlew compileJava` only when the user asked for a full check: it regenerates and writes
files. Then report every DSL validation warning, `ERROR` and `SKIP(user-modified...)` line, any
compile error, and the files regeneration changed (`git status` afterwards) - generated code that
was committed out of step with the DSL. Leave the files as regeneration wrote them and say so. Without
that request, say that you did not build and what the user would run.

## 5. Business impact

Per entity, before and after: what is stored, who may do what (`@access`, `@owner`), the lifecycle
(`states:`), what is calculated (`@compute`, `@snapshot`), which API operations exist (`@expose`).

Flag for a decision: wider access or a removed `@owner`; `@login` / `@password` changes; a removed
or renamed field; a narrowed type; a removed state or move; a removed API operation; a changed key.

## Your report

1. **Findings**, most serious first, each with `file:line`, what goes wrong and where the change
   belongs: *blocker* (security, data loss, rules the generator ignores, drift from the DSL, does
   not compile), *should fix*, *note*.
2. **What changes for the business**, as in section 5, readable without Java.
3. **Checked**: which generator the build runs, what you ran and its result, or that you did not build.
